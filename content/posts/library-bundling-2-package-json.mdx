`package.json` 이라고 하면 무엇이 떠오르는가? `name`, `version`, `scripts`, 그리고 의존성 목록. 패키지의 이름표이자 설치 명세서 정도로 여기기 쉽다.

라이브러리를 배포해 본 사람이라면 한 번쯤 이런 이슈를 받아봤을 것이다. "함수 하나 썼는데 번들이 200KB 늘었어요." "`lib/utils` 를 import 하면 모듈을 못 찾는대요." "React 훅이 `Invalid hook call` 로 죽어요." 코드는 한 줄도 안 바꿨는데 소비자 쪽에서만 터지는 문제들이다.

보통 이런 문제는 소비자의 번들러 설정 탓이라고 생각한다. 웹팩이 이상하다거나, Vite 가 CJS 를 못 다룬다거나.

진짜 원인은 대부분 내 `package.json` 에 있다. 소비자의 번들러와 Node 의 모듈 로더는 내 코드를 읽기 전에 이 파일을 먼저 읽는다. 어느 파일을 진입점으로 삼을지, 어느 모듈을 안심하고 잘라내도 되는지, 어느 패키지를 소비자 것과 공유할지를 전부 여기서 결정한다.

**`package.json` 은 메타데이터가 아니라 소비자의 도구가 실행하는 계약이다.** 이 글에서는 그 계약의 세 조항, `exports`, `sideEffects`, `dependencies` 를 값을 하나씩 바꿔가며 소비자 번들이 어떻게 달라지는지 잰다. 모든 수치는 예시 저장소 `library-bundling-examples` 의 `episodes/02-package-json/` 에서 재현할 수 있다.

## exports 필드

1편에서 만든 라이브러리의 `package.json` 을 다시 보자.

```json
{
  "name": "@ep2/lib-exports-ok",
  "type": "module",
  "exports": {
    ".": {
      "types": "./dist/index.d.ts",
      "import": "./dist/index.js",
      "require": "./dist/index.cjs"
    },
    "./utils": {
      "types": "./dist/utils.d.ts",
      "import": "./dist/utils.js",
      "require": "./dist/utils.cjs"
    },
    "./package.json": "./package.json"
  }
}
```

`exports` 는 **이 패키지에서 밖으로 열린 경로의 전체 목록**이다. 여기 적힌 경로만 `import` 할 수 있고, 적히지 않은 경로는 파일이 존재해도 막힌다. Node 의 해석기가 실제로 어떻게 판단하는지 다섯 가지 경우를 돌려봤다.

```
$ node app/scripts/exports.mjs
1) subpath        : …/lib-exports-ok/dist/utils.cjs
2) 미등록 경로     : ERR_PACKAGE_PATH_NOT_EXPORTED
3) require, ok    : …/lib-exports-ok/dist/index.cjs
4) require, broken: …/lib-exports-broken/dist/index.js
5) import, ok     : file:///…/lib-exports-ok/dist/index.js
```

하나씩 읽어보자.

**1) 서브패스.** `@ep2/lib-exports-ok/utils` 는 `"./utils"` 항목에 매핑되어 `dist/utils.cjs` 로 풀린다. 소비자는 실제 파일 위치를 몰라도 되고, 나는 나중에 파일을 옮겨도 `exports` 만 유지하면 된다.

**2) 캡슐화.** `dist/internal.js` 는 배포물에 분명히 들어 있지만 `exports` 에 없으므로 `ERR_PACKAGE_PATH_NOT_EXPORTED` 로 막힌다. `exports` 가 없던 시절에는 소비자가 `lib/dist/internal/whatever.js` 같은 내부 경로에 의존할 수 있었고, 그러면 내부 파일 하나 옮기는 것이 breaking change 가 됐다. `exports` 는 그 문을 닫는다.

**3)~5) 조건 분기.** `require()` 로 가져오면 `require` 조건이, `import` 로 가져오면 `import` 조건이 선택된다. 여기까지는 예상대로다. 문제는 4번이다.

`lib-exports-broken` 은 `lib-exports-ok` 와 소스도 산출물도 완전히 같다. 다른 것은 `exports` 안 키의 **순서**뿐이다.

```json
{
  "exports": {
    ".": {
      "default": "./dist/index.js",
      "require": "./dist/index.cjs",
      "types": "./dist/index.d.ts"
    }
  }
}
```

`require()` 로 가져왔는데 결과는 `dist/index.js`, 즉 ESM 파일이다. 조건은 **위에서부터 처음 맞는 것이 이긴다.** `default` 는 모든 조건에 맞으므로 맨 위에 두면 그 아래는 영영 선택되지 않는다. Node 24 는 `require(esm)` 을 지원해서 이 경우 에러 없이 돌아가긴 하지만, 그건 우연이다. 정성껏 만든 CJS 산출물은 아무도 읽지 않는다.

같은 이유로 `types` 는 **항상 맨 위**에 둔다. TypeScript 도 같은 규칙으로 조건을 고르는데, `import` 가 먼저 매칭되어 `.js` 파일로 풀리면 그 옆에서 `.d.ts` 를 찾는 폴백에 기대게 된다. tsdown 처럼 `.js` 옆에 `.d.ts` 를 나란히 내는 도구를 쓰면 대개 넘어가지만, 타입 파일을 다른 폴더에 두거나 `.d.cts` 와 `.d.ts` 를 나눠 내는 순간 깨진다. 순서를 `types` → `import` / `require` → `default` 로 고정하면 고민할 일이 없다.

`"./package.json": "./package.json"` 한 줄도 넣어두자. 번들러 플러그인이나 툴링이 패키지 버전을 읽으려고 이 경로를 자주 요청한다.

## sideEffects

1편에서 ESM 은 tree-shaking 을 "가능하게" 할 뿐 "보장"하지는 않는다고 했다. 무엇이 그 보장을 막는지 보자.

**부작용(side effect)** 은 모듈이 평가되는 순간 바깥세상에 일으키는 변화다. 전역 변수에 무언가를 등록하거나, 폴리필을 설치하거나, CSS 를 주입하거나. 이런 코드는 아무도 그 모듈에서 값을 가져오지 않아도 **평가되는 것 자체가 목적**이다.

```ts
// lib-side-effects/src/register.ts
type Registry = { plugins: string[] };
const g = globalThis as unknown as { __registry?: Registry };
g.__registry ??= { plugins: [] };
g.__registry.plugins.push("side-effects-lib");

export const registry: Registry = g.__registry;
```

문제는 번들러가 부작용을 **증명할 수 없다**는 데 있다. 위 코드는 딱 봐도 부작용이지만, 아래 코드는 어떤가.

```ts
// lib-side-effects/src/b.ts
function buildTable(): number[] {
  return Array.from({ length: 256 }, (_, i) => (i * 31) % 257);
}
const TABLE: number[] = buildTable();

export function b(x: number): number {
  return TABLE[x & 255];
}
```

`buildTable()` 은 순수하지만, 번들러는 함수 본문을 끝까지 따라가 순수성을 증명하지 않는다. 최상위에서 함수를 **호출**했다는 사실만으로 "부작용이 있을지도 모른다"고 판단하고 남긴다. 남겨야 안전하기 때문이다.

`sideEffects` 필드는 이 판단을 라이브러리 저자가 대신 내려주는 장치다. `false` 면 "이 패키지의 모든 파일은 부작용이 없으니, 가져온 이름이 없는 파일은 통째로 버려도 된다"는 선언이고, 배열이면 "이 파일들만 부작용이 있다"는 뜻이다.

라이브러리는 `a`, `b`, `c`, `register` 네 파일을 배럴 `index.ts` 가 다시 내보내는 구조이고, 소비자는 `a` 하나만 가져온다. `sideEffects` 값만 네 가지로 바꿔 소비자 번들을 쟀다.

```ts
// app/src/side-effects-*.ts
import { a } from "@ep2/lib-side-effects-…";

console.log(a(1));
```

| lib 의 `sideEffects` | 앱 번들 | `__registry` 등록 코드 | `b`, `c` 의 최상위 호출 |
|---|---|---|---|
| 미설정 | 646 B | 남음 | 남음 |
| `false` | 160 B | **사라짐** | 사라짐 |
| `["./dist/register.js"]` | 164 B | **사라짐** | 사라짐 |
| `["./dist/register.js", "./dist/index.js"]` | 340 B | 남음 | 사라짐 |

네 줄이 각각 다른 교훈을 준다. 막대로 놓고 보자.

<SideEffectsDemo />

**미설정** 은 가장 크다. 번들러는 모든 파일에 부작용이 있을 수 있다고 가정하고, `b` 와 `c` 의 `buildTable()`, `compile()` 호출까지 전부 남긴다. 가져온 건 `a` 하나인데 646 B 다.

**`false`** 는 가장 작지만 **잘못됐다.** `register.js` 의 등록 코드가 사라졌다. 소비자는 `import { a }` 만 했으니 `registry` 를 안 쓴다고 판단해 `register.js` 를 통째로 버렸고, 전역 등록은 일어나지 않는다. 플러그인이 등록되지 않고, CSS 가 주입되지 않는 버그가 이 모양으로 생긴다. 파일 크기만 보면 성공처럼 보여서 더 위험하다.

**`["./dist/register.js"]`** 는 부작용 파일을 정확히 지목했는데도 사라졌다. 이게 이 실험에서 가장 놀란 결과다. 이유는 탐색 순서에 있다. 소비자는 `index.js` 를 가져오고, `index.js` 는 목록에 없으므로 "부작용 없음"이다. 번들러는 부작용 없는 모듈에서 쓰이지 않는 내보내기(`registry`)를 만나면 **그 너머로 가지 않는다.** `register.js` 는 목록에 있지만 도달하지 못했으므로 존재하지 않는 것과 같다.

**`["./dist/register.js", "./dist/index.js"]`** 로 배럴까지 목록에 넣으면 그제서야 등록 코드가 남는다. 동시에 `b`, `c` 의 최상위 호출은 잘려 나가서 340 B 로 끝난다. 필요한 것만 남은 정답 상태다.

실전에서는 세 가지를 지키면 된다.

1. 최상위에서는 선언만 하고, 실행은 함수 안으로 미룬다. 그러면 `sideEffects: false` 를 마음 놓고 쓸 수 있다.
2. 부작용이 꼭 필요하면(CSS, 폴리필, 플러그인 등록) **배럴로 흘리지 말고 별도 진입점**으로 낸다. `import "lib/register"` 처럼 소비자가 명시적으로 가져오게 하면 탐색 문제가 사라진다. CSS 라면 `"sideEffects": ["**/*.css"]` 가 관례다.
3. 최상위 호출인데 순수하다고 확신하면 `/* @__PURE__ */` 를 붙인다. 번들러는 이 주석이 붙은 호출을 미사용 시 제거한다. 1편의 CJS 산출물에 tsdown 이 `__commonJSMin(...)` 앞에 붙여둔 것이 바로 이 주석이다.

## 의존성은 어디에 두는가

`package.json` 에는 의존성을 적는 칸이 셋이다.

| 필드 | 뜻 | 소비자가 설치하나 | 내 번들에 넣나 |
|---|---|---|---|
| `dependencies` | 런타임에 필요하다 | 그렇다, 자동으로 | 기본은 넣지 않는다 (external) |
| `peerDependencies` | 소비자가 이미 갖고 있어야 한다 | 소비자 책임 | **절대** 넣지 않는다 |
| `devDependencies` | 빌드·테스트에만 쓴다 | 아니다 | 흔적이 없어야 한다 |

"내 번들에 넣나" 열이 번들링의 관심사다. tsdown 은 `dependencies` 와 `peerDependencies` 에 적힌 패키지를 기본적으로 **external** 로 둔다. 산출물에는 그 패키지의 코드 대신 `import` 문 한 줄만 남는다.

작은 이벤트 이미터 `@ep2/tiny-dep` 에 의존하는 라이브러리를 두 가지로 빌드했다. 하나는 기본값(external), 하나는 tiny-dep 을 산출물 안으로 끌어넣은 것(inline)이다.

```ts
// lib-deps-inline/tsdown.config.ts
export default defineConfig({
  entry: ["src/index.ts"],
  format: "esm",
  deps: { alwaysBundle: ["@ep2/tiny-dep"] },
});
```

두 산출물의 첫 줄부터 다르다.

```js
// lib-deps-external/dist/index.js (410 B)
import { Emitter } from "@ep2/tiny-dep";
// …

// lib-deps-inline/dist/index.js (934 B)
var Emitter = class {
  // tiny-dep 전체가 여기 복사된다
};
// …
```

라이브러리 크기만 보면 external 이 작은 게 당연하다. 진짜 차이는 소비자 앱에서 난다. 앱이 이 라이브러리만 쓰는 경우와, 앱도 tiny-dep 을 직접 쓰는 경우로 나눠 쟀다.

| 소비자 앱 | inline 라이브러리 | external 라이브러리 |
|---|---|---|
| 앱은 라이브러리만 쓴다 | 1,007 B | 1,060 B |
| 앱도 tiny-dep 을 직접 쓴다 | **1,670 B** | 1,154 B |

첫 줄은 거의 같다. tiny-dep 이 라이브러리 안에 있든 밖에 있든 결국 앱 번들에 한 번 들어간다. 둘째 줄이 갈린다. inline 라이브러리는 자기 안에 tiny-dep 을 복사해 두었으므로, 앱이 가져온 tiny-dep 과 **같은 코드가 두 벌** 들어간다. 산출물을 열어보면 `Emitter` 와 `Emitter$1` 이 나란히 있다. external 이었다면 소비자 번들러가 하나로 합쳤을 것이다.

그래서 기본값은 external 이다. 의존성을 인라인하는 것은 소비자의 중복 제거 기회를 뺏는 일이고, 그 패키지의 보안 패치를 소비자가 받을 수 없게 만드는 일이기도 하다. 예외는 아주 작고 버전 노출이 무의미한 헬퍼 정도다.

## React가 두 벌이 되는 이유

의존성 중에서도 `react` 같은 프레임워크는 별도의 규칙을 따른다. 앱은 react 19 를 쓰는데, react 를 쓰는 라이브러리 둘을 설치했다. 하나는 react 를 `dependencies` 에, 하나는 `peerDependencies` 에 적었다.

```json
// lib-react-dep/package.json
{ "dependencies": { "react": "18.3.1" } }

// lib-react-peer/package.json
{ "peerDependencies": { "react": ">=18" } }
```

```
$ node duplicate-react/app/run.mjs
app react            : 19.2.4
lib (dependencies)   : 18.3.1 same instance? false
lib (peerDependencies): 19.2.4 same instance? true
```

두 방식이 앱 안에서 어떤 모양이 되는지 그려보면 이렇다.

<DuplicateReactDemo />

왼쪽은 `dependencies` 다. 패키지 매니저는 라이브러리가 요구한 react 18 을 라이브러리 전용으로 따로 설치한다. `node_modules/.pnpm` 에 `react@18.3.1` 과 `react@19.2.4` 가 나란히 생기고, 라이브러리의 컴포넌트는 앱과 **다른 React 인스턴스** 위에서 돈다. 훅은 "지금 렌더 중인 React" 를 모듈 스코프에서 찾는데, 그 React 가 둘이면 서로를 못 본다. 이것이 `Invalid hook call` 과 "Hooks can only be called inside the body of a function component" 의 가장 흔한 원인이다.

오른쪽은 `peerDependencies` 다. 라이브러리는 react 를 설치하지 않고 **앱의 것을 빌려 쓴다.** `same instance? true` 가 그 증거다. 인스턴스가 하나이므로 훅도, 컨텍스트도, `instanceof` 도 전부 정상이다.

규칙은 단순하다. **소비자와 반드시 같은 인스턴스를 공유해야 하는 패키지는 `peerDependencies` 에 둔다.** React, Vue, 상태 관리 라이브러리, ORM 처럼 전역 상태를 갖거나 `instanceof` 로 서로를 확인하는 것들이 여기 해당한다. 없어도 되는 선택적 통합이라면 `peerDependenciesMeta` 에 `optional: true` 를 함께 적는다.

## files 필드

마지막으로 짧게. `files` 는 **배포 tarball 에 들어갈 것**의 목록이다.

```json
{ "files": ["dist"] }
```

이 한 줄이 없으면 `.gitignore` 에 없는 모든 파일이 올라간다. 소스, 테스트, 예시, 때로는 `.env` 까지. 배포 전에 `npm pack --dry-run` 으로 무엇이 들어가는지 한 번 눈으로 확인하는 습관을 들이자. 이 확인을 자동화하는 도구들은 3편에서 다룬다.

## 정리

- `exports` 는 열린 경로의 전체 목록이자 캡슐화 장치다. 조건은 **처음 맞는 것이 이기므로** `types` 를 맨 위에, `default` 를 맨 아래에 둔다.
- `sideEffects: false` 는 크기를 줄이지만 진짜 부작용도 함께 지운다. 부작용 파일만 목록에 적어도 **배럴에서 탐색이 멈추면** 도달하지 못한다. 부작용은 별도 진입점으로 낸다.
- `dependencies` 는 external 이 기본이다. 인라인하면 소비자 번들에 같은 코드가 두 벌 들어간다(1,154 B → 1,670 B).
- 인스턴스를 공유해야 하는 패키지는 `peerDependencies` 다. `dependencies` 에 두면 React 가 두 벌이 되고 훅이 깨진다.
- `files` 로 배포 범위를 좁힌다.

재현은 예시 저장소 루트에서 다음을 실행하면 된다.

```bash
pnpm install && pnpm -r --filter "@ep2/*" build
node scripts/size.mjs episodes/02-package-json/app/dist/*/*.js
grep -c __registry episodes/02-package-json/app/dist/side-effects-*/*.js
(cd episodes/02-package-json/app && node scripts/exports.mjs)
(cd episodes/02-package-json/duplicate-react/app && node run.mjs)
```

다음 편에서는 산출물의 마지막 조각인 타입 선언과, 배포 전에 이 모든 계약이 지켜졌는지 기계적으로 검증하는 방법을 다룬다. tsdown 이 tsc 를 어디까지 대신하는지도 거기서 정리한다.

타입 선언 파일이라고 하면 무엇이 떠오르는가? tsc 가 컴파일하면서 옆에 떨어뜨려 주는 부산물. JS 만 제대로 나오면 따라오는 것.

라이브러리를 설치했는데 자동완성이 안 뜨고 모든 것이 any 인 경험을 해봤을 것이다. 혹은 잘 되던 타입이 moduleResolution 을 node16 으로 바꾸는 순간 "Could not find a declaration file" 로 무너지는 경험도. 라이브러리 저자 쪽에서는 아무것도 바꾼 게 없는데 말이다.

보통 이럴 때 소비자의 tsconfig 가 까다롭다고 생각한다. 실제로도 그렇게 답변이 달린 이슈가 많다.

하지만 d.ts 는 JS 와 별개의 산출물이고, TypeScript 는 d.ts 를 JS 와 **같은 규칙으로** 해석한다. 파일 확장자가 .d.ts 냐 .d.cts 냐가 ESM 이냐 CommonJS 냐를 결정하고, package.json 의 exports 조건이 어느 타입 파일을 줄지 결정한다. 1편과 2편에서 JS 산출물에 적용됐던 모든 규칙이 타입에도 그대로 적용된다.

**타입 선언은 두 번째 배포물이다.** 이 글에서는 타입이 잘못 배포되는 세 가지 형태를 재현하고, tsdown 이 tsc 를 어디까지 대신하는지 재고, 배포 전에 이 모든 것을 기계적으로 검사하는 방법을 정리한다. 수치는 예시 저장소 [library-bundling-examples](https://github.com/hovelopin/library-bundling-examples) 의 `episodes/03-types-and-publish/` 에서 재현할 수 있다.

## 타입도 모듈 포맷을 탄다

1편에서 tsdown 은 `dist/index.js` 와 `dist/index.cjs` 를 냈고, 그 옆에 index.d.ts 와 index.d.cts 도 함께 냈다. 왜 타입 파일이 둘인가.

TypeScript 는 .d.ts 파일을 옆에 있는 `.js` 파일의 포맷으로 해석한다. package.json 이 `"type": "module"` 이면 .d.ts 는 ESM 모듈의 타입이다. CommonJS 산출물의 타입은 .d.cts 여야 한다. 확장자가 곧 포맷이다.

타입을 어디에 적을지 생각하면, types 를 블록 맨 위에 하나만 두는 형태가 가장 먼저 떠오른다.

```json
{
  "exports": {
    ".": {
      "types": "./dist/index.d.ts",
      "import": "./dist/index.js",
      "require": "./dist/index.cjs"
    }
  }
}
```

조건은 위에서부터 매칭되니 types 를 맨 앞에 두면 어느 소비자든 타입을 찾을 것 같다. 직접 써봐도 문제가 드러나지 않는다. 그런데 이 package.json 을 **arethetypeswrong**(attw) 에 넣으면 이렇게 나온다.

```
$ attw --pack .

👺 Import resolved to an ESM type declaration file, but a CommonJS JavaScript file.

┌───────────────────┬─────────────────────────┐
│ node10            │ 🟢                      │
│ node16 (from CJS) │ 👺 Masquerading as ESM  │
│ node16 (from ESM) │ 🟢 (ESM)                │
│ bundler           │ 🟢                      │
└───────────────────┴─────────────────────────┘
```

require() 로 들어온 소비자에게도 조건은 위에서부터 매칭된다. 첫 줄의 types 가 잡히고, 그 값은 index.d.ts, 즉 ESM 의 타입이다. JS 는 index.cjs 를 받았는데 타입은 ESM 것을 받은 것이다. TypeScript 는 이 모듈을 ESM 이라고 믿고, CommonJS 파일에서 require 하는 코드에 엉뚱한 에러를 낸다. attw 는 이 상태를 "ESM 인 척한다(Masquerading as ESM)" 고 부른다. publint 도 같은 것을 잡는다.

```
pkg.exports["."].types types is interpreted as ESM when resolving with the
"require" condition. … Consider splitting out two "types" conditions for
"import" and "require", and use the .cts extension
```

고치는 방법은 포맷별로 types 를 **분기 안에** 넣는 것이다.

```json
{
  "main": "./dist/index.cjs",
  "types": "./dist/index.d.ts",
  "exports": {
    ".": {
      "import": {
        "types": "./dist/index.d.ts",
        "default": "./dist/index.js"
      },
      "require": {
        "types": "./dist/index.d.cts",
        "default": "./dist/index.cjs"
      }
    },
    "./package.json": "./package.json"
  }
}
```

각 분기 안에서 types 가 default 보다 먼저 온다. 규칙은 그대로다. "처음 맞는 것이 이긴다" 를 분기마다 적용할 뿐이다. 포맷별 분기 형태로 바꾸면 attw 가 네 칸 모두 🟢 를 찍는다. 1편과 2편의 예시가 이 모양이었던 이유가 여기 있다.

맨 위의 main 과 types 는 exports 를 모르는 오래된 해석기(attw 의 node10 행)를 위한 폴백이다. 없어도 최신 도구는 다 동작하지만, 1편 라이브러리에 attw 를 돌리면 node10 행이 💀 로 찍힌다. 두 줄이면 끝나는 일이니 넣어두자.

## 타입이 아예 없는 경우

더 흔한 경우는 다음과 같다.

```json
{
  "types": "./dist/index.d.ts",
  "exports": {
    ".": {
      "import": "./dist/index.js",
      "require": "./dist/index.cjs"
    }
  }
}
```

exports 에 types 가 없고, 최상위 types 만 있다. index.d.cts 는 만들지 않았다. 이 상태의 라이브러리(`lib-broken-types`)를 attw 에 넣으면 `node16 (from CJS)` 칸에 ❌ No types 가 찍힌다. exports 가 있으면 최상위 types 는 무시되고, require 분기에는 타입이 없으며, index.cjs 옆에 index.d.cts 도 없기 때문이다.

문제는 이 라이브러리가 **대부분의 환경에서 멀쩡하다**는 점이다. bundler 해석에서는 import 분기가 잡혀 index.js 옆의 index.d.ts 를 찾는다. ESM 프로젝트에서도 같다. 저자가 Vite 나 Next.js 로 테스트했다면 문제를 볼 수 없다. CommonJS 프로젝트에서 node16 해석을 쓰는 소비자만 이 에러를 만난다.

```
error TS7016: Could not find a declaration file for module '@ep3/lib-broken-types'.
'…/dist/index.cjs' implicitly has an 'any' type.
```

한 환경에서 되는 것과 모든 환경에서 되는 것은 다르다. attw 의 표가 4행인 이유도 여기에 있다. 각 행이 실제로 존재하는 소비자 환경 하나씩이다.

## 타입이 새는 경우

세 번째 형태는 d.ts 안에서 일어난다. 2편의 작은 이벤트 이미터 tiny-dep 을 **devDependencies** 에 두고, 그 타입을 public API 에 노출하는 라이브러리를 만들었다.

```ts
// lib-type-leak/src/index.ts
import { Emitter } from "@ep2/tiny-dep";

type BusEvents = { message: string };

export function createBus(): Emitter<BusEvents> {
  return new Emitter<BusEvents>();
}
```

JS 산출물에는 Emitter 가 인라인되어 실행에 문제가 없다. 그런데 d.ts 의 첫 줄은 이렇다.

```ts
// lib-type-leak/dist/index.d.ts
import { Emitter } from "@ep2/tiny-dep";
```

소비자에게는 tiny-dep 이 없다. devDependencies 는 설치되지 않으니까. 소비자의 tsc 는 이렇게 무너진다.

```
node_modules/@ep3/lib-type-leak/dist/index.d.ts(1,25):
  error TS2307: Cannot find module '@ep2/tiny-dep' or its corresponding type declarations.
check.ts(2,28):
  error TS7006: Parameter 'm' implicitly has an 'any' type.
```

두 번째 에러가 더 고약하다. 소비자가 skipLibCheck 를 켜두면(대부분 켠다) 첫 번째 에러는 조용히 사라지고 두 번째만 남는다. 소비자는 자기 코드에 any 가 생긴 이유를 라이브러리 d.ts 첫 줄에서 찾아야 한다.

대응은 둘 중 하나다. Emitter 타입이 public API 라면 패키지를 dependencies 로 올린다. 아니면 d.ts 를 번들해서 선언을 인라인한다. tsdown 은 후자를 기본으로 해준다. type-leak 실험에서는 일부러 `dts.neverBundle` 로 번들링을 껐다. tsc 로 d.ts 를 내면 항상 import 가 남는다. tsc 는 d.ts 를 번들하지 않는다.

## tsdown은 tsc를 어디까지 대신하나

여기까지 오면 자연스럽게 묻게 된다. tsdown 을 쓰면 tsc 는 필요 없는 것 아닌가.

tsc 가 하는 일을 넷으로 쪼개면 답이 보인다.

| tsc 의 일            | tsdown 이 대신하나           |
| -------------------- | ---------------------------- |
| 타입 검사            | 하지 않는다                  |
| 트랜스파일 (TS → JS) | 한다                         |
| d.ts 생성            | 한다                         |
| 번들링               | 한다 (tsc 는 애초에 못 한다) |

첫 줄이 핵심이다. tsdown 을 포함한 고속 도구(oxc, esbuild, swc)는 **파일 하나만 보고 타입 문법을 잘라낸다.** 다른 파일을 읽지 않으니 빠르지만, 그래서 "이 함수에 넘긴 인자가 맞는 타입인가" 를 원리상 판단할 수 없다. 속도는 타입 검사를 포기해서 얻은 것이지 tsc 를 더 잘 만들어서 얻은 것이 아니다.

그런데 d.ts 생성은 타입 추론이 필요한 일이다. `function f(x: number) { return x + 1 }` 의 반환 타입이 number 라는 것을 알아야 `f(x: number): number` 를 쓸 수 있다. 파일 하나만 보고 지우는 도구가 어떻게 d.ts 를 만드는가.

두 가지 길이 있다. 하나는 내부에서 TypeScript 컴파일러 API 를 호출하는 것이다. 사실상 tsc 를 안에서 돌린다. 다른 하나는 **isolatedDeclarations** 다. TypeScript 5.5 가 추가한 옵션으로, 모든 export 에 반환 타입을 명시하도록 강제한다. 추론할 것이 없으면 파일 단위로 d.ts 를 뽑을 수 있다.

```ts
// isolatedDeclarations 가 요구하는 형태 — 반환 타입이 전부 적혀 있다
export function make000(name: string, score: number = 0): Record000 {
  return { id: 0, name, tags: [], score };
}
```

두 길의 비용을 쟀다. 모듈 1,000개(각각 인터페이스 하나와 함수 넷)짜리 라이브러리를 생성해 다섯 가지 방법으로 빌드하고, 각 3회의 중앙값을 취했다.

<DtsBenchDemo />

| 방법                       | 중앙값   | d.ts 에 든 시간    |
| -------------------------- | -------- | ------------------ |
| tsc --emitDeclarationOnly  | 698 ms   | 698 ms (검사 포함) |
| tsdown · generator: tsc    | 1,655 ms | 1,478 ms           |
| tsdown · generator: oxc    | 1,041 ms | 864 ms             |
| tsdown · dts 없음 (기준선) | 177 ms   | —                  |
| tsc --noEmit (검사만)      | 533 ms   | —                  |

tsdown 행은 JS 번들(esm+cjs)까지 포함한 시간이라 기준선 177 ms 를 빼야 d.ts 비용이 나온다. TS 컴파일러 API 로 만들면 1,478 ms, oxc 로 만들면 864 ms 다. 그리고 tsdown 은 d.ts 1,000개를 파일 하나로 합치는 일까지 하므로 tsc 의 698 ms 와 나란히 놓을 수는 없다.

숫자보다 중요한 것은 구조다. oxc 경로는 타입 검사를 **하지 않고** 864 ms 를 썼다. 타입 검사만 따로 하면 533 ms 가 더 든다. 즉 tsdown 으로 빌드하는 프로젝트는 타입 검사를 별도로 돌려야 하고, 그것이 곧 tsc 의 남은 역할이다.

```json
{
  "scripts": {
    "build": "tsdown",
    "typecheck": "tsc --noEmit",
    "prepublishOnly": "npm run typecheck && npm run build"
  }
}
```

tsc 를 컴파일러가 아니라 **린터로 강등시켜 쓰는 것**이다. 에디터가 보여주는 빨간 줄과 CI 가 잡는 에러를 일치시키는 역할이고, 산출물은 tsdown 이 만든다.

isolatedDeclarations 는 부수 효과도 있다. public API 의 타입이 전부 코드에 적혀 있으니, 리팩터링으로 반환 타입이 바뀌면 그 자리에서 드러난다. 추론에 기대던 API 는 저자도 모르는 사이에 바뀔 수 있다.

## 배포 전에 기계가 검사하는 것

여기까지 세 가지 형태의 타입 문제와 두 가지 도구를 봤다. 배포 전 검증 절차로 정리하면 세 단계다.

**publint** 는 package.json 의 정적 규칙을 본다. 조건 순서, 확장자와 포맷의 불일치, files 누락 같은 것을 배포물을 만들지 않고도 잡는다. 올바른 라이브러리에서는 `All good!` 한 줄이다.

**attw** 는 해석 매트릭스를 본다. 실제로 npm pack 한 tarball 을 네 가지 소비자 환경으로 해석해 각 칸에 결과를 찍는다. 위에서 본 표들이 attw 출력의 전형적인 예다. `--pack .` 으로 로컬에서 돌릴 수 있고, tsdown 은 `--attw` 플래그로 빌드 직후 자동으로 돌려준다(`--publint` 도 있다).

**스모크 테스트** 는 소비자가 되어 본다. 워크스페이스 링크는 소비자의 환경이 아니다. devDependencies 가 전부 있고, 심볼릭 링크 너머로 이웃 패키지가 보인다. npm pack 으로 tarball 을 만들어 빈 프로젝트에 설치한 뒤 import, require, tsc 를 돌려보는 스크립트를 하나 두면 위의 세 문제가 전부 걸린다.

```
$ node smoke/run.mjs

@ep3/lib
  ✔ import  ✔ require  ✔ tsc bundler  ✔ tsc node16 esm  ✔ tsc node16 cjs

@ep3/lib-broken-types
  ✔ import  ✔ require  ✔ tsc bundler  ✔ tsc node16 esm
  ✘ tsc node16 cjs   error TS7016: Could not find a declaration file for module …

@ep3/lib-type-leak
  ✔ import
  ✘ tsc bundler      error TS2307: Cannot find module '@ep2/tiny-dep' …
```

마지막으로 npm pack --dry-run 을 눈으로 본다. 2편에서 말한 files 필드의 효과가 여기서 보인다. 예시 라이브러리는 `files: ["dist"]` 로 5개 파일이 올라간다. 지우면 12개가 된다. 벤치 스크립트, 생성기, tsconfig 여러 벌이 소비자에게 배달된다. npm 은 files 가 없으면 `.gitignore` 를 대신 읽는데, 그래서 소스 폴더는 빠지고 설정 파일은 남는 어중간한 결과가 나온다.

## 배포 전 체크리스트

세 편을 목록 하나로 접으면 이렇다.

- 지원하는 런타임과 모듈 포맷을 정하고 README 에 적었다. 가능하면 ESM 만 낸다 (1편)
- exports 로 열린 경로를 전부 적었고, 포맷별 분기 안에 types 를 먼저 두었다 (2·3편)
- 최상위 main 과 types 폴백을 두었다 (3편)
- sideEffects 를 정확히 적었고, 부작용은 배럴이 아니라 별도 진입점으로 낸다 (2편)
- 인스턴스를 공유해야 하는 패키지는 peerDependencies 에 있다 (2편)
- devDependencies 의 타입이 public d.ts 에 남지 않는다 (3편)
- `tsc --noEmit` 이 CI 에서 돈다 (3편)
- publint 와 attw 가 통과한다 (3편)
- npm pack 한 tarball 로 import / require / tsc 스모크를 돌렸다 (3편)
- files 로 배포 범위를 좁혔고 npm pack --dry-run 을 확인했다 (2·3편)

## 정리

- d.ts 는 JS 와 같은 해석 규칙을 탄다. .d.ts 는 ESM, .d.cts 는 CommonJS 의 타입이고, exports 의 조건은 타입에도 그대로 적용된다. types 조건 하나를 맨 위에 두면 require 소비자가 ESM 타입을 받는다.
- 타입 문제는 **한 환경에서 보이지 않는다.** attw 의 4행 매트릭스가 소비자 환경을 대신 돌아준다.
- tsdown 은 트랜스파일·d.ts·번들을 대신하지만 **타입 검사는 하지 않는다.** `tsc --noEmit` 은 남는다. isolatedDeclarations 를 켜면 d.ts 생성이 타입 검사 없이 파일 단위로 돌아간다.
- 배포 전에 publint, attw, npm pack 스모크 세 가지를 돌린다. 세 줄이면 이 시리즈의 모든 문제가 걸린다.

재현은 예시 저장소 루트에서 다음을 실행하면 된다. 편별 실행법과 확인 포인트는 [episodes/03-types-and-publish](https://github.com/hovelopin/library-bundling-examples/tree/main/episodes/03-types-and-publish) 의 README 에 정리해 뒀다.

```bash
pnpm install && pnpm -r --filter "@ep3/*" build
pnpm --filter @ep3/lib bench
pnpm --filter "@ep3/lib*" attw
pnpm --filter @ep3/smoke start
```

세 편에 걸쳐 본 것은 결국 하나다. 라이브러리의 산출물은 내 코드가 아니라 **남의 빌드의 입력**이고, 그 형태를 정하는 것이 package.json 과 빌드 설정이다. 코드보다 package.json 과 빌드 설정을 먼저 잡으면 나머지는 도구가 검사해준다.

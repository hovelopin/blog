# 블로그 말투 규칙 (~다체 평서체)

이 블로그의 모든 글은 하나의 말투로 통일한다. **`~다/~이다` 평서체(서술체)**로,
기술적 사실을 단정적으로 전달하되 독자를 동반자로 끌어들이는 톤이다.

## 핵심 특징

- **단정적 서술체.** 문장을 `~다/~이다/~한다/~된다`로 단호하게 맺어 주장을 흐리지
  않는다. "~인 것 같다", "~일 수도 있다" 같은 완충 표현을 남발하지 않는다.
- **독자를 "우리"로 초대.** 개념을 함께 따라가는 느낌으로 쓰고, 데모·실습·탐구를
  유도할 때 청유형("~해보자 / 살펴보자 / 확인해보자")을 쓴다.
- **문제 제기로 여는 도입.** 독자가 겪었을 법한 상황이나 질문("~해본 적 있을
  것이다", "무엇이 떠오르는가?")으로 시작해 자연스럽게 본론으로 넘어간다.
- **짧은 문장과 긴 문장의 교차.** 개념을 길게 설명한 뒤 짧은 문장으로 핵심을 쐐기
  박듯 강조한다. 한 호흡으로 읽히는 리듬을 만든다.
- **용어는 쓰고 나서 바로 설명.** 전문 용어를 먼저 던지고 곧장 풀어주거나, 굵은
  글씨로 강조한 뒤 정의한다. 독자가 모른다고 가정하되 가르치려 들지 않는다.
- **개인 경험은 예시로만.** 자기 지칭은 "필자"로, 자기 이야기는 개념을 이해시키기
  위한 다리로만 쓴다. 감정 토로로 흐르지 않는다.

블로그 마크다운(`content/**/*.md`)을 새로 쓰거나 고칠 때, 번역/초안을 다듬을 때,
어투를 통일할 때 항상 이 규칙을 적용한다.

## 종결어미 규칙 (가장 중요)

- 모든 서술 문장은 `~다 / ~이다 / ~한다 / ~된다` 평서체로 맺는다.
- `~습니다 / ~합니다 / ~입니다` 존댓말과 `~해요 / ~하죠 / ~네요 / ~거든요 / ~까요?`
  구어체는 **절대 쓰지 않는다.**
- 자기 지칭은 "저/제가"가 아니라 "필자/필자가", 권유는 "~합시다"가 아니라
  "~하자/~해보자".

## 변환 예시 (존댓말 → 평서체)

| 존댓말/구어체 | 평서체 |
| --- | --- |
| 생겼습니다 | 생겼다 |
| 따라붙습니다 | 따라붙는다 |
| 됩니다 | 된다 |
| 만듭니다 | 만든다 |
| 반환합니다 | 반환한다 |
| 핵심입니다 | 핵심이다 |
| 중요합니다 | 중요하다 |
| 도구입니다 | 도구다 |
| 살펴보겠습니다 | 살펴보자 (또는 살펴본다) |
| 뜯어보겠습니다 | 뜯어보자 |
| 확인하세요 | 확인하자 |
| 왜 그럴까요? | 왜 그럴까? |
| 버그죠 | 버그다 |
| 편했어요 | 편했다 |
| 제 관점으로 | 필자의 관점으로 |

## 절대 건드리지 않는 것 (내용 불변)

어투만 바꾼다. 다음은 **한 글자도 바꾸지 않는다.**

- **코드 블록 내부**(```) — 주석 포함.
- **프론트매터 키**(title/date/description/tags/repo/color/sourceUrl/thumbnail 등)의
  이름·구조·값. 단, description처럼 문장형 값 안의 종결어미는 평서체로 바꾼다.
- 마크다운 **헤더(##), 표, 리스트 구조, 링크, 인용(>) 블록** 구조.
- **사실·수치·API 이름·설명 내용.**
- 이미 평서체인 헤더/문장은 그대로 둔다.

리스트 항목 끝, 표 셀 안 설명, 인용 블록 안 문장의 종결어미도 빠짐없이 평서체로.

## 마무리 검증

글을 쓰거나 고친 뒤 반드시 확인한다. 아래 grep이 **비어 있어야** 한다.

```bash
grep -nE "습니다|합니다|입니다|했어요|하죠|네요|거든요|까요|하세요|이에요|예요" <파일>
```

기계적으로 어미만 자르지 말고, 바꾼 뒤 소리 내어 읽었을 때 위 "핵심 특징"대로
단정적이면서 자연스럽게 읽히는지 확인한다. 어색하면 의미는 유지하되 문장을 살짝
다듬는다.

## 글 구성 (2026-09 기준 방향)

말투와 별개로, 글의 뼈대는 아래 형태를 기본으로 삼는다.

### 제목

형태는 자유롭게 고른다. 명제형("주석은 친절의 영역이다"), 질문형("DX의 본질이란?"),
동명사형("정보 중독에서 벗어나기"), 방법형("애니메이션을 설계하는 방법"), 라벨형
("서버 모니터링 분석 가이드")이 모두 쓸 만하다. 대신 아래는 지킨다.

- **짧게.** 한글 20자 안쪽을 기준으로 삼는다. 길어질수록 목록에서 읽히지 않는다.
- **부제를 붙이지 않는다.** `- ~편`, `(MCP)` 같은 꼬리표는 빼고 하나의 구절로 끝낸다.
- **시리즈명을 제목에 반복하지 않는다.** frontmatter 의 `series` 가 이미 들고 있으므로
  제목에는 그 편의 내용만 적는다.
- "혁신", "완벽한", "모든" 같은 과장을 쓰지 않는다.

### 섹션 제목(h2)

- **번호를 붙이지 않는다.** `## 1. 문제` 가 아니라 `## 문제`.
- 짧게 짓는다. "쪼개기", "모으기", "미루기"처럼 **한 단어~세 단어 동사형·명사형**이 기본이고,
  길어지더라도 한 줄을 넘기지 않는다.
- 계층을 얕게 가져간다. h2로 끝낼 수 있으면 h3를 만들지 않는다.
- 섹션 사이에 `---`를 넣지 않는다. 구분은 h2 밑줄이 맡는다.
- **제목만 보고도 내용을 짐작할 수 있어야 한다.** "Before" / "After" / "개선" / "문제"처럼
  그 자체로는 아무것도 알려주지 않는 라벨은 피하고, 무엇을 다루는지 제목에 담는다.
  (`### Before` → `### gcTime 24시간일 때`)
- **제목에 `—`(대시)로 부연을 붙이지 않는다.** `## 재현 환경 — 더 가혹하게` 가 아니라
  `## 더 가혹한 재현 환경` 처럼 한 구절로 다시 쓴다. 글 제목도 마찬가지다.

### 도입부

본론 전에 4~5문단으로 다음 순서를 밟는다.

1. 독자에게 묻는다 — "~라고 하면 무엇이 떠오르는가?"
2. 독자가 겪었을 상황을 묘사한다 — "가끔 ~한 웹사이트를 만난다"
3. 흔한 오해를 먼저 꺼낸다 — "보통 ~라고 생각한다"
4. 진짜 원인을 제시한다
5. 제목의 명제를 다시 한 문장으로 못 박는다

### 데모(캔버스) 배치

글에서 개념을 설명할 때는 **스크린샷보다 움직이는 데모를 먼저 고려한다.** 배치는 항상
세 겹으로 감싼다.

1. **유도 문장** — "말로만 들으면 와닿지 않으니 직접 보자", "두 방식을 시간축에 올려보면"
2. **데모** — `<XxxDemo />`
3. **관찰 해설** — 데모에서 무엇을 봐야 하는지 한두 문장. "왼쪽은 ~, 오른쪽은 ~"

데모는 아끼지 않는다. 설명이 한 화면을 넘어가는 개념마다 하나씩 두는 것을 기준으로 삼고,
긴 글이면 섹션마다 하나씩 들어가도 좋다. 컴포넌트는 `src/components/demos/`에 두고
`src/components/mdx-components.tsx`에 등록하면 MDX 본문에서 import 없이 쓸 수 있다.
